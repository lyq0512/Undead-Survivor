## 3. 已完成且必须保持的功能

以下是前序用户验收通过的功能背景，不代表新对话已经重新运行验证。

### 3.1 菜单与游戏流程

```text
主菜单 → 角色选择 → 选择已解锁角色 → 开始游戏
主菜单 → 设置 → 返回主菜单
游戏中 → 暂停菜单 → Resume → 继续当前局
游戏中 → 暂停菜单 → 设置 → Back → 暂停菜单
游戏中 → 暂停菜单 → Characters → 场景重载 → 角色选择
```

- 角色选择场景对象仍叫 `GameStart`，不要误认为缺少 CharacterSelectPanel 对象而重复创建。
- 返回选人结束当前局，通过重新加载场景清理敌人、武器和数值。
- 成就与音量持久化保留；选人页 Back 仍可返回主菜单。
- 升级选择与胜负结算期间，不允许正常打开游戏内暂停菜单。

### 3.2 UI 封装

- 四个业务面板均挂有 UIPanel，并由控制器负责导航。
- 用户明确选择的默认时长：**打开 0.4 秒，关闭 0.3 秒**。不要改回 0.18／0.12。
- 动画使用 `Time.unscaledDeltaTime`，游戏暂停时仍播放。
- 动画期间禁止面板按钮交互，并阻挡下层点击；完成隐藏后解除阻挡。
- 控制器通过 `isTransitioning` 防止重复导航。
- 暂停立即生效，Resume 的关闭动画完成后才恢复游戏。
- 初始化隐藏状态仍使用立即显隐；当前没有缩放动画，不必主动添加。
- 四个面板根对象保持激活，通过 CanvasGroup 控制隐藏，不通过取消 Active 来隐藏。
- CanvasGroup 透明不等于脚本停止运行；也不能直接视作 Canvas 已停止重建。

### 3.3 战场与 HUD 分区

```text
Canvas
├─ GameplayView：RawImage，显示摄像机输出
├─ HUD
│  ├─ TopBar
│  │  ├─ Exp
│  │  └─ InfoRow
│  │     ├─ Kill → Kill Text
│  │     ├─ Timer
│  │     ├─ Level
│  │     └─ GameMenuButton
│  └─ Health
├─ Joy
├─ LevelUp
├─ GameResult
├─ Notice
└─ TitleScreenRoot
   ├─ MainMenuPanel
   ├─ SettingsPanel
   ├─ GameStart
   └─ PauseMenuPanel
```

- 当前 TopBar 高度为 20 个 UI 单位，经验条高度为 4。
- 经验条曾因缩到 2 而出现显示问题，恢复 4 后正常；不要无依据再次缩小或改动其内部 Sprite。
- 游戏中 GameplayView 为 TopBar 留空间；菜单与角色选择时恢复铺满，避免顶部黑条。
- Main Camera 输出到运行时 Render Texture；Virtual Camera 负责镜头控制。
- Pixel Perfect Camera 会管理摄像机显示区域，不能简单改 Camera.rect 就假定分区生效。
- GameplayRenderTexture 是模板。运行时尺寸由 GameplayViewController 按实际显示区域计算，不固定为模板的 270 × 500。
- Canvas 的参考分辨率已有像素风配置，历史记录为 135 × 270。先核对，不为调整一个按钮而整体修改。

## 4. 必须区分的事实与待验证项

### 已观察到的候选项

| 候选项 | 当前实现记录 | 不应直接得出的结论 |
| --- | --- | --- |
| 索敌 | Scanner.FixedUpdate 使用 CircleCastAll 返回数组 | 不能据此认定它是整帧最大的耗时 |
| HUD | LateUpdate 轮询并 string.Format | 不能直接承诺事件化后提高多少 FPS |
| 成就 | LateUpdate 检查条件及 PlayerPrefs | 不能只为菜单动画而重写全部成就系统 |
| 对象池 | List 数组查找失活对象，池不足时 Instantiate | 不能假定已有 Queue、Return、Release 或静态 instance |
| 图集 | 前序扫描未找到独立 Sprite Atlas 资源 | 不能假定每张动画帧都是独立纹理；已有精灵表 |
| Render Texture | 按显示尺寸创建，尺寸变化时重建 | 不能假定一个 RawImage 就意味着整个世界只有一次 Draw Call |

### 尚未取得的信息

- 正式目标平台、最低设备档位与目标帧率。
- 目标设备上的 CPU／GPU 帧时间和稳定性。
- 各场景持续 GC Alloc、绘制统计及 UI 重建成本。
- 实际运行时纹理尺寸、内存及场景重载后的变化。
- 敌人高峰时主要受脚本、物理、提交绘制还是像素处理限制。

第一阶段必须补齐相关基线，不填写虚构数据，不用编辑器截图代替真机性能结论。

## 5. 修改约束与指导方式

### 5.1 工程保护

1. 先读取当前文件和 Git 状态，辨认用户已有改动；不执行清理、重置或覆盖来获得“干净环境”。
2. 文档整理时发现 ProjectSettings/ProjectSettings.asset 有未提交改动、Docs/ 为未跟踪目录。此状态可能变化，进入新对话必须重新检查；不要自行归因或丢弃。
3. 序列化字段、Inspector 引用、PlayerPrefs Key 和按钮事件不随意改名。
4. 音量字段 `sfxbgmVolume` 虽然名称不理想，但保留原名。
5. 音量 Key：`UndeadSurvivor.Audio.BgmVolume`、`UndeadSurvivor.Audio.SfxVolume`；成就 Key：`MyData`、`unlockJasper`、`unlockTater`。实施前核对源码。
6. 不直接修改 Library/PackageCache；可只读查看安装版本的实际实现。
7. 不为减少 Draw Call 破坏精灵透明排序、角色动画、灯光或 UI 九宫格。
8. 不同时重写对象池、经验系统、UI 架构和渲染管线。
9. 项目规范与现有实现不一致时，说明差异并制定迁移方案，不假装接口已经存在。

### 5.2 每轮指导模板

```text
性能优化第 N 步：本步目标

1. 是否需要停止 Unity 运行；是否先保存。
2. 打开哪个文件，或选中哪个 Hierarchy 对象。
3. 定位到哪段现有代码／哪个组件。
4. 本次只修改什么；提供完整且可编译的代码或准确字段数值。
5. 保存、等待编译、查看 Console。
6. 运行时预期结果及本步需要记录的数据。
7. 异常时提供什么截图／错误；先停在此处解决。
8. 等待用户回复“第 N 步完成”，再进入下一步。
```

运行模式下的临时 Inspector 改动通常不会保存。若用于实验，必须明确标注，并说明停止运行后是否需要重新设置。

## 6. 分阶段实施路线

### 阶段 A：只读检查与性能基线（必须先做）

- 确认当前场景、已验收版本和已有改动，记录基线版本。
- 确认目标设备和帧率；不确定时先记录编辑器环境，不把它当最终性能标准。
- 指导打开 Profiler，先采集正常战斗；下一小步再学习查看 CPU 和 GC。
- 后续分步采集敌人较多、菜单动画、升级选择和场景重载数据。
- 使用 Frame Debugger 检查代表性的一帧，解释绘制顺序和拆批原因。
- 有目标设备后采集 Development Build，并记录性能分析工具本身的开销。
- Device Simulator 只用于布局，不视作模拟设备真实性能。

完成条件：能依据样本指出主要成本及证据。没有数据时不进入“大规模优化”。

### 阶段 B：选择一个可验证的优化任务

按测量结果选一个任务；下表不是强制固定顺序。

| 任务 | 触发条件 | 可能涉及的文件 | 完成标准 |
| --- | --- | --- | --- |
| B1 索敌无分配 | 查询相关 GC 或耗时明显 | Scanner.cs | 无持续结果数组分配，最近目标正确，缓冲区满载策略明确 |
| B2 HUD 刷新 | 格式化分配或 UI 更新成本明显 | HUD.cs、GameManager.cs、相关数值写入处 | 仅变化时刷新；时间按显示精度更新；经验、血量与等级无漏刷 |
| B3 成就事件化 | 每帧检查不符合规范或有可测成本 | AchieveManager.cs、GameManager.cs、Enemy.cs 等 | 条件与旧存档不变；无重复解锁；事件订阅正确清理 |
| B4 对象池改进 | 扩容峰值或线性查找成本明显 | PoolManager.cs、生成和回收调用点 | 回收接口完整迁移；预热可控；无重复归还、状态残留或引用失效 |
| B5 图集与材质 | Frame Debugger 显示可避免的拆批 | Sprite Atlas、精灵导入配置、材质 | 正确排序与画面保留；绘制成本有改善；内存无不合理膨胀 |
| B6 UI Canvas 组织 | UI 重建成本明显 | 场景 Canvas 结构、HUD 和菜单引用 | 以实测收益证明拆分合理；不盲目给每个面板或按钮加 Canvas |
| B7 纹理与渲染分辨率 | GPU、带宽或纹理内存受限 | GameplayViewController.cs、Render Texture、导入设置、Follow.cs | 比例、像素边缘、血条映射正确；收益有数据支撑 |

使用安装版本支持的 Physics2D 非分配查询 API，不能直接复制过时的 API 用法。需要降频时同时验证远程武器响应；缓冲区容量不足时不能悄悄漏掉关键目标。

事件化前枚举所有数值写入路径，例如受伤、治疗、击杀、升级、初始状态和场景重载。只在一个位置广播而遗漏其他写入者，会造成 HUD 错误。

对象池改为空闲队列时，当前 SetActive(false) 约定不能继续无迁移地使用，否则对象不会自动进入新队列。需要同时梳理 Enemy.Dead、Bullet 碰撞／越界与武器子物体的生命周期。

### 阶段 C：单任务对比与回归

每个任务必须完成：

1. 明确本次假设，例如“减少 Scanner 每物理帧的结果数组分配”。
2. 列出本次改动文件、序列化影响及验收条件。
3. 一小步一小步指导实施并处理编译问题。
4. 使用相同设备、分辨率和场景条件重新采样。
5. 比较相关指标，不只看瞬时 FPS 或 Draw Call 数量。
6. 回归菜单、暂停、开局、存档及战斗相关功能。
7. 用户确认后记录结论与版本，才进入下一个任务。

不要求为所有低影响改动编写自动化测试；优先采用有意义的性能采样和功能回归。复杂的对象池及事件生命周期改动，再按风险设计必要测试。

### 阶段 D：真机与长时间验证

- 在目标设备验证热量、分辨率、帧率上限等条件对结论的影响。
- 连续运行高峰战斗及多次返回选人，观察对象、纹理和内存是否持续不合理增长。
- 对最终发布配置复核体验，不把分析构建的开销直接当成发布表现。
- 对无明确收益、损害清晰度或影响玩法的改动重新评估，不为统计数字保留无效优化。

## 9. 当前交接结论与新对话第一步
