## 1. 目标与边界

本文解释 Draw Call、合批、纹理、像素与性能优化之间的关系，并给出适合本项目的实施路径。

本次仅建立文档，不修改业务脚本、场景、材质、纹理或渲染管线设置。文中的优化收益属于待验证假设，不能理解为已经确认项目存在帧率问题，或优化后必然提升某个百分比。

后续实施遵循根目录 [PROJECT_RULES.md](../PROJECT_RULES.md)：

- 保留现有 public、SerializeField 字段名，避免 Inspector 引用丢失。
- 不在 Update、FixedUpdate 中创建集合、使用 LINQ、频繁拼接字符串或查找组件；高频 LateUpdate 同样需要检查。
- 数值变化优先采用事件通知，避免每帧轮询。
- 敌人、弹幕及高频特效统一经过对象池。
- 保留现有菜单、暂停、音量存档、角色解锁及重新开局流程。

## 2. 概念总览

| 概念 | 简单解释 | 本项目中的应用 |
| --- | --- | --- |
| Draw Call | CPU 向图形接口提交的一次绘制请求 | 绘制地图、敌人、武器、UI |
| 合批 | 将满足条件的绘制组织到一起，减少绘制次数或状态准备成本 | 精灵图集、共享材质、UI 绘制组织 |
| Texture | 渲染时读取的图像数据 | 角色图片、地图、UI 图片 |
| Sprite | 图片中用于 2D 显示的一个区域，包含切片等信息 | 单帧角色动画、敌人动画帧 |
| Material | 决定采用哪个 Shader 及其参数、纹理 | 精灵和 UI 的绘制方式 |
| Render Texture | 接收摄像机等渲染结果的纹理 | GameplayView 显示的实时游戏画面 |
| 像素 | 图像或屏幕上的采样单元 | 像素风清晰度、内部渲染分辨率 |
| 性能优化 | 减少完成同等游戏体验所需的时间和资源 | CPU、GPU、GC、显存、物理及 UI 优化 |

不能将这些概念直接画等号：对象少不一定 Draw Call 少；Draw Call 少不一定 GPU 快；图片文件小不一定运行时显存小；像素风不一定低开销。

## 3. 当前项目的渲染与 UI 结构

当前摄像机与界面协作关系为：

```text
角色、敌人、地图、武器等游戏世界
                 ↓
Main Camera（Cinemachine 跟随、Pixel Perfect 配置）
                 ↓
运行时 Render Texture
                 ↓
Canvas 下的 GameplayView（RawImage）
                 ↓
HUD、摇杆、菜单等 UI 在其上方显示
```

GameplayViewController 负责在菜单中铺满画面，在游戏中为 TopBar 留出空间。它按照显示区域尺寸与 Canvas 缩放计算运行时纹理尺寸，尺寸变化时重新创建纹理，并在销毁时释放资源。

因此，GameplayRenderTexture 资源里的初始宽高不是运行时固定分辨率。游戏世界仍然先被摄像机正常绘制，之后再通过 RawImage 显示；不能把最后的一个 RawImage 理解为整个游戏只有一次 Draw Call。

四个业务面板使用 UIPanel 统一控制显隐与淡入淡出：

- MainMenuPanel：主菜单。
- GameStart：角色选择。
- SettingsPanel：音量设置。
- PauseMenuPanel：游戏内暂停菜单。

当前动画默认打开 0.4 秒、关闭 0.3 秒，使用非缩放时间。UIPanel 管理透明度、交互和状态；TitleScreenController 管理导航及游戏生命周期。此次封装不等于合批，也不会自动隔离 Canvas 重建。

## 4. Draw Call：理解和测量

### 4.1 哪些条件可能导致拆开绘制

即使看起来是同一类对象，也可能因为纹理、材质、Shader 变体、透明排序、遮罩、灯光或渲染通道不同而拆开。透明物体还必须保持正确的前后关系，不能为了合批任意改变层级或 Sorting Order。

100 个敌人不必然是 100 次 Draw Call，也不保证都能合成一次。实际结果应通过 Frame Debugger 确认。

### 4.2 需要同时关注的指标

| 指标 | 用途 | 注意事项 |
| --- | --- | --- |
| CPU Main Thread 时间 | 判断脚本、物理、UI 等主线程成本 | 区分实际工作与等待、同步时间 |
| CPU Render Thread 时间 | 判断绘制提交及状态准备成本 | 不能单独用 Draw Call 数量解释全部耗时 |
| GPU 时间 | 判断像素处理、特效和渲染通道成本 | 是否可采集取决于设备、API 和分析工具 |
| Batches / Draw Calls | 观察绘制组织及数量 | 不脱离具体渲染管线解释统计值 |
| SetPass Calls | 观察 Shader Pass 设置情况 | 作为线索，不单独作为优化结论 |
| GC Alloc | 查找持续的托管内存分配 | 追踪到具体调用位置 |
| Texture / Render Texture 内存 | 判断图像资源及输出画面的成本 | 包括格式、深度、抗锯齿等因素 |
| UI 重建耗时 | 判断动态 HUD 和界面更新的影响 | 在 Profiler 中查看实际调用样本 |

Profiler 用来定位时间花在哪里，Frame Debugger 用来解释某一帧的绘制顺序和拆批原因。两者需要结合使用。[Unity 渲染性能分析文档](https://docs.unity.com/en-us/engine/6000.6/manual/analysis/graphics-performance-profiling/profile-rendering)

### 4.3 合理的目标

若目标是 60 FPS，每帧预算约 16.67 ms；30 FPS 则约 33.33 ms。这是预算换算，不是当前项目已达成的指标。

CPU 与 GPU 存在并行和同步关系，不能简单把两个时间相加作为一帧耗时。应在目标设备上确认瓶颈，并为系统波动和敌人高峰留出余量。

## 5. 合批方案

### 5.1 Sprite Atlas

Sprite Atlas 将多个精灵组织到图集中，减少切换纹理的机会，为合批提供条件。[Unity Sprite Atlas 文档](https://docs.unity.com/en-us/engine/6000.0/manual/unity2d/sprite/atlas/atlas-introduction)

目前项目的角色、敌人已有包含多帧动画的精灵表；扫描 Assets 时未找到独立的 .spriteatlas 或 .spriteatlasv2 资源。不能把“没有独立图集资源”等同于“每帧动画都使用不同纹理”。

建议先评估两类资源：

| 图集分组 | 候选内容 | 组织原则 |
| --- | --- | --- |
| 战斗精灵图集 | 常用玩家、敌人、武器精灵 | 按实际共同出现和加载生命周期分组 |
| UI 图集 | 图标、按钮、面板装饰 | 保留现有 Sprite 引用和九宫格边框信息 |

实施前后使用同等场景对比 Draw Call、CPU 渲染耗时、图集页数和内存。进入同一图集不保证一次绘制，图集也可能因为尺寸限制分成多页。

不要将所有资源无差别打成一个大图集。过大的图集可能让当前界面连带加载大量不用的资源。

### 5.2 材质与排序

- 优先共享兼容的材质，避免为每个敌人创建独立材质实例。
- 后续编写变色或受伤效果时，注意访问 Renderer.material 可能创建材质副本。
- 不为降低统计值而破坏透明排序、武器层级或角色遮挡关系。
- URP 的 2D 灯光、法线等效果是否影响批次，需要结合实际 Renderer 配置测量。

### 5.3 SRP Batcher 与其他合批方式

SRP Batcher 主要降低 CPU 准备和提交兼容绘制时的成本，不应理解成一定减少 Draw Call 数量。[Unity SRP Batcher 说明](https://unity.com/blog/engine-platform/srp-batcher-speed-up-your-rendering)

动态合批、静态合批和 GPU Instancing 具有各自条件，不是统一勾选就一定收益。会移动、会回池的敌人和弹幕不应直接按静态物体处理。第一阶段优先查图集、材质和实际拆批原因，不盲目切换所有渲染选项。

### 5.4 UI 合批与 Canvas 重建

Image、字体文字和 RawImage 可能使用不同纹理，不能假定它们都能合批。遮罩及中间穿插的绘制内容也可能影响批次。

动态 HUD 与静态菜单是否拆成不同 Canvas，应通过 UI 重建成本决定。增加子 Canvas 能隔离部分重建范围，但也形成独立批次边界，不能给每个按钮都加 Canvas。[Unity UI 优化建议](https://create.unity3d.com/Unity-UI-optimization-tips)

现有 CanvasGroup 淡入淡出保持不变。隐藏面板应解除射线阻挡；透明度为零不代表业务脚本停止运行。需要停掉后台业务时，应通过生命周期或事件订阅管理，而不是仅依赖透明度。

## 6. 纹理：内存、清晰度与设置

### 6.1 图片文件大小不等于运行时内存

以未压缩 RGBA32、无 Mipmap 的单张纹理为例：

```text
内存约等于：宽 × 高 × 每像素字节数
2048 × 2048 × 4 = 16 MiB
```

实际成本还受平台压缩格式、Mipmap、Read/Write、副本和资源生命周期影响。完整 Mipmap 链在常见二维情形下大约额外增加三分之一的纹理数据，不能仅凭 PNG 文件体积估算显存。

### 6.2 本项目的导入检查项

| 设置 | 当前建议 | 例外与验证 |
| --- | --- | --- |
| Filter Mode | 像素风素材优先 Point | 最终以屏幕上的清晰度为准 |
| Mipmap | 固定视角像素精灵通常可关闭 | 大幅缩小或缩放视野时评估闪烁与采样质量 |
| Read/Write | 没有 CPU 读写需求时关闭 | 使用 GetPixels、SetPixels 等功能时另行判断 |
| PPU | 保持现有素材的比例关系 | 不通过改 PPU 减少显存 |
| 平台压缩 | 按目标设备测试 | 检查像素边缘、颜色与透明度是否失真 |
| Max Size | 满足资源原始需求 | 不无差别降低，避免精灵细节丢失 |

当前抽查的敌人、角色精灵使用 PPU 18、Point 过滤，并关闭 Mipmap 和 Read/Write。后续不需要为了“优化”反复修改这些已经合理的配置。

Read/Write 启用可能保留额外的 CPU 可访问像素数据；这些设置的定义见 [Unity 纹理导入文档](https://docs.unity.com/en-us/engine/6000.0/manual/materials-and-shaders/textures/textures-reference/texture-type-sprite)。

### 6.3 Render Texture 的专项评估

当前方案用于适配 Pixel Perfect Camera 与独立战场区域，保留现有功能，不立即重写。

评估内容：

1. 记录实际运行时纹理宽高，而不是只记录模板尺寸。
2. 测量颜色缓冲、深度缓冲和其他渲染目标的内存。
3. 记录场景重载和设备尺寸切换后，纹理数量、内存是否回落。
4. 若 GPU 或带宽成为瓶颈，再评估降低内部渲染分辨率。
5. 降低分辨率时保持画面比例，并验证血条坐标映射、像素一致性和 UI 边界。

如果宽和高都降低到原来的一半，像素数量变为四分之一，但这不代表总帧耗时也会缩到四分之一。脚本、物理及绘制提交成本可能基本不变。

## 7. 像素与像素风

### 7.1 三种尺寸需要分开理解

| 概念 | 含义 | 修改后的主要影响 |
| --- | --- | --- |
| 素材像素 | 原图由多少像素组成 | 美术细节与纹理数据 |
| Pixels Per Unit | 多少素材像素对应一个世界单位 | 精灵在世界中的尺寸 |
| 屏幕／渲染像素 | 实际输出画面包含多少采样点 | 清晰度、像素处理量和缓冲内存 |

PPU 18 表示 18 个素材像素对应一个世界单位。改变 PPU 不会减少原图像素数，也不直接降低纹理显存。

### 7.2 清晰度原则

- 保持素材像素密度与摄像机设置相互匹配。
- Point 过滤有助于保留硬边缘，但不能解决任意比例缩放导致的像素宽度不一致。
- Pixel Perfect 配置、显示区域比例和内部渲染尺寸需要共同验证。
- UI 继续采用已验收的淡入淡出；缩放动画可能暂时产生不规则像素，作为可选视觉效果单独评估。
- 高分辨率设备上的像素风仍可能有大量像素处理工作。

### 7.3 透明覆盖与 Overdraw

同一屏幕位置被多次绘制称为过度绘制。大面积透明图片、半透明菜单背景、摇杆和特效重叠，都可能增加像素处理成本。

本项目需要检查暂停遮罩、菜单背景和 RawImage 的叠加范围，但不为降低透明覆盖而破坏正常显示。暂停时世界仍会渲染，Time.timeScale 为零不会自动停止摄像机渲染。

## 8. 当前代码中的优化候选项

以下事实由静态检查得到；实际耗时和优先级必须由 Profiler 验证。

| 位置 | 已观察到的实现 | 建议方案 | 重点验收 |
| --- | --- | --- | --- |
| Scanner.cs | FixedUpdate 调用 CircleCastAll，接收新数组 | 使用预分配缓冲区的 Physics2D 查询；评估扫描间隔 | 稳态查询不持续分配；最近目标正确；结果满缓冲区有处理策略 |
| HUD.cs | LateUpdate 轮询数值并格式化文字 | 血量、经验、击杀、等级事件驱动；时间显示按秒更新 | 显示及时；经验升级清零正确；暂停时不重复构造相同文本 |
| AchieveManager.cs | LateUpdate 检查成就及存档状态 | 监听击杀与胜利事件，达成时保存和通知 | 旧存档保留；不会重复解锁或重复提示 |
| PoolManager.cs | List 数组、线性查找失活对象，缺少空闲对象时 Instantiate | 基于容量数据预热；评估空闲队列和明确归还接口 | 无重复归还；位置、血量、速度及动画状态正确重置 |
| Enemy.cs | 每次启用重新查找玩家刚体；受击启动击退协程 | 缓存稳定引用；按实测热点评估受击处理 | 不将所有 GetComponent 一概视为必然 GC；受击和重用行为保持一致 |
| GameplayViewController.cs | 显示尺寸变化时重建纹理 | 测量实际分辨率、重建次数、释放情况 | 不在尺寸未变时重复分配；菜单与战场比例正确 |
| UIPanel.cs | 切换期间运行淡入淡出协程 | 保留现有方案，测量动画时 UI 和透明混合开销 | 不要求一次性切换操作绝对零分配；无持续泄漏和点击穿透 |

项目规范描述 PoolManager 为单例及 Queue 实现，当前源码实际使用 GameManager.pool 访问和 List 数组。后续改造应以实际实现为起点，不能直接假设已有 Return、Release 或静态 instance 接口。

## 9. 测量与实施流程

### 9.1 准备基线

1. 保存已通过功能验收的版本，建立独立优化分支。
2. 记录设备型号、系统、分辨率、图形 API、目标帧率及构建方式。
3. 首轮使用 Profiler 定位；Deep Profile 会增加开销，只在需要追踪调用时短时使用。
4. 对目标设备上的 Development Build 采样；最终再用发布配置复核体验。
5. 预热后采样固定时长，例如每种场景 30 秒；优化前后保持条件一致。
6. 将正常战斗与生成、升级、打开菜单、重载场景等瞬时事件分开记录。

Device Simulator 用于布局检查，不能代替目标手机的 CPU、GPU 和内存性能测试。

### 9.2 建议覆盖场景

| 编号 | 场景 | 关注项 |
| --- | --- | --- |
| S1 | 主菜单静止 | 后台脚本、摄像机渲染、基础内存 |
| S2 | 正常战斗 | 稳态脚本、物理、GC 和绘制 |
| S3 | 敌人与弹幕较多 | 索敌、碰撞、动画、池扩容、GPU |
| S4 | 升级三选一 | 暂停行为、文字刷新、界面成本 |
| S5 | 暂停菜单与设置反复切换 | UI 重建、透明覆盖、事件与动画 |
| S6 | 返回选人并重新开局，重复三轮 | 对象和纹理释放、事件订阅、内存趋势 |
| S7 | 改变设备显示尺寸 | 纹理重建、布局、像素清晰度 |

### 9.3 优化记录模板

| 项目 | 优化前 | 优化后 |
| --- | --- | --- |
| 测试版本／提交号 | 待采集 | 待采集 |
| 设备、分辨率、API | 待采集 | 保持一致 |
| 测试场景与采样时长 | 待采集 | 保持一致 |
| 敌人／弹幕数量 | 待采集 | 保持一致 |
| CPU 主线程／渲染线程 ms | 待采集 | 待采集 |
| GPU ms（可采集时） | 待采集 | 待采集 |
| 稳态 GC Alloc／帧 | 待采集 | 待采集 |
| 帧时间中位数、P95 与异常峰值 | 待采集 | 待采集 |
| Draw Calls／Batches／SetPass | 待采集 | 待采集 |
| 纹理及 Render Texture 内存 | 待采集 | 待采集 |
| 功能与画面回归 | 基线通过 | 待验证 |

P95 表示约 95% 的采样帧不超过该耗时，用于观察稳定性。不要用单个瞬时 FPS 截图证明优化收益；运行中是否受 VSync、帧率上限和温度影响也应记录。

### 9.4 推荐实施顺序

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| P0 | 建立 Profiler、Frame Debugger 和内存基线 | 能说明主要成本来自哪里 |
| P1 | 处理已测得的索敌、HUD 等持续分配 | 对应稳态分配减少，行为不变 |
| P2 | 成就事件化、对象池和物理热点 | 高峰帧时间或相关耗时改善 |
| P3 | 图集、材质和 UI Canvas 组织 | 实测拆批或重建成本改善，内存可接受 |
| P4 | Render Texture 分辨率和平台纹理配置 | GPU／内存收益明确，像素显示通过验收 |

如果首轮测量证明 GPU 已是主要瓶颈，可以提前处理 P3、P4。每次只改变一类因素，提交并记录对比结果，未产生收益或破坏视觉时应重新评估方案。

## 11. 当前结论

本项目可以分别应用 Draw Call 分析、合批、纹理管理、像素清晰度控制和 CPU／内存优化。现有菜单与画面分区功能已经建立，下一阶段的合理起点是采集基线，而不是立即修改全部资源设置。

目前可以确认源码中存在持续分配、数值轮询和对象池线性查找等候选项；尚不能确认真实设备上的首要瓶颈，也不能承诺具体帧率收益。后续按测量结果实施，每项优化同时保留性能记录与功能回归结果。
